# LP 수집 이력 보관 운영

LP 공고 원문·첨부 근거를 버리지 않고 실행별 반복 보관을 줄인다. 공개 사업, 원문 문서 버전, 검토 결정과 실행 행의 식별자는 유지한다. 이 문서는 코드 계약이며 실제 적용 수치와 실행 근거는 `docs/lp_collection_status.md`를 따른다.

## 보관 범위

- 최신 실행 3개와 `program_state.run_id`는 DB에 전체 보고서를 유지한다. 현재 실행이 최신 3개 밖이어도 보호한다.
- 그 외 큰 보고서는 비공개 Supabase Storage의 `lp-collection-reports`에 보관한다. 256KiB 이상 문자열과 `attachment_bytes`의8KiB 이상 PDF/OLE/ZIP base64 문자열은 내용 SHA256을 기준으로 한 번만 저장하고, 실행별 목록이 원래 JSON의 위치를 가리킨다. 일반 공고 HTML은 실행별 압축 목록 안에 유지해 작은 파일별 왕복 요청을 줄인다. 중간 크기 첨부는 strict base64와 파일 서명으로 저장 방식만 선택하며 원래 문자열을 재인코딩하지 않는다. 일반 HTML·잘못된 base64는 원문 그대로 목록에 유지한다. 기존8KiB 방식과256KiB inline 보관본도 같은 디코더로 복원하며 재작성하지 않는다.
- 파일 업로드 후 인증된 다운로드로 원문 전체를 복원해 길이와 SHA256을 확인한다. 한 실행 안에서는 검증한 동일 청크의 압축 바이트를 최대64MiB 메모리 캐시에 재사용하며 매 참조의 길이/지문을 다시 검사한다. 목록·버킷·접근 차단 검사는 캐시하지 않고, 다음 실행은 빈 캐시로 시작한다. 공개키로 파일을 읽을 수 없다는 검사까지 통과해야 DB 보고서를 보관 위치 기록으로 바꾼다.
- DB 행·외래키·수집 문서·공개 HTML·검토 결정은 삭제하지 않는다. 실패하면 치환 전 원문을 유지한다. 업로드 뒤 경쟁 상태로 치환을 건너뛰어도 검증된 파일을 자동 삭제하지 않는다.
- 비공개 버킷과 함께 해당 버킷만 대상으로 하는 restrictive RLS 정책을 사용한다. `anon`과 `authenticated`는 보관 파일을 읽거나 쓸 수 없다. 다른 서비스 버킷의 정책과 데이터는 바꾸지 않는다. 운영 키는 수집·보관 작업에만 둔다.

## 동시 실행과 복원

압축·업로드·다운로드 중 DB 연결을 유지하지 않는다. 치환 직전에 발행/검토와 같은 잠금을 잡고 현재 실행·최신 실행 3개를 다시 확인하며, 대상 행의 버전이 그대로일 때만 변경한다. 복원도 전체 파일을 검증한 후 같은 보관 위치/행 버전인 경우에만 원래 보고서를 되돌린다. 공개 상태나 검토 결정을 변경하지 않는다.

과거 검토 결정은 자체 evidence를 갖는다. 현재 검토 화면과 결정 함수가 읽는 보고서는 항상 DB에 전체 내용으로 유지한다. 복원된 과거 보고서는 다음 정기 보관 때 다시 보관될 수 있다.

## 실행 방법

모든 실제 DB/Storage 작업은 `Maintain LP report storage` workflow에서 수행한다. 수동 점검/공간 회수는 정기 수집과 같은 `lp-program-collection` 대기열을 사용한다. 자동 보관은 `lp-report-retention` 대기열로 분리해 예약 수집의 대기 실행을 교체하지 않는다. 치환은 여전히 DB의 발행 잠금과 행 버전 검사로 보호한다. 기본 모드는 읽기 전용 `inspect`다. 결과 artifact에는 수치·식별자·해시만 넣고 원문과 비밀값은 넣지 않는다.

```sh
gh workflow run maintain-lp-report-storage.yml -f mode=inspect
gh workflow run maintain-lp-report-storage.yml -f mode=archive -f limit=1
gh workflow run maintain-lp-report-storage.yml -f mode=verify -f limit=100
gh workflow run maintain-lp-report-storage.yml -f mode=restore -f run_id=검증대상실행ID
```

첫 적용은 1건 보관·전체 복원 검증·실제 DB 복원 후 확대한다. 유지할 최신 개수는 최소3, 업로드 전 Storage 예산은900MB로 제한한다. 파일 누락·지문 불일치·공개 접근 가능·현재 자료 변경·예산 초과는 실패로 남긴다.

## 실제 디스크 공간 회수

보고서 치환만으로 PostgreSQL 파일 크기가 즉시 줄지는 않는다. 최초 대량 보관 뒤 `reclaim`은 모든 보관 파일을 다시 검증하고 LP 실행 이력 테이블만 재작성한다.

```sh
gh workflow run maintain-lp-report-storage.yml -f mode=reclaim -f limit=100
```

이 작업은 session/autocommit 전용 연결과 발행 잠금을 사용한다. 잠금 대기는5초, 실행 제한은180초이며 잠금 획득 후 살아 있는 보고서 크기가256MiB 이하인지 다시 검사한다. 공개 페이지 테이블이나 다른 서비스 테이블을 재작성하지 않는다.

정기 수집·복구가 끝나면 별도의 유지보수 workflow가 최대5건을 보관하고 LP 실행 이력과 큰 단일 공개상태 행의 일반 VACUUM으로 재사용 가능한 공간을 정리한다. 새 보관 후보가0개여도 이미 보관본이 있으면 정리를 수행해 실패한 발행의 빈 공간도 회수 대상으로 둔다. 원 실행은 같은 저장소의 main에서 실행한 schedule/workflow_dispatch만 허용하며 PR·fork 실행을 받지 않는다. 자동 유지보수는 수집의25분 제한을 소비하지 않고 자체 대기열에서 직렬 실행한다. 일반 VACUUM의 쿼리 제한은5초로, 발행의20초 잠금 대기보다 먼저 종료·잠금 반환한다. 수동 FULL 회수만180초 제한을 사용한다. 정기 작업에서 강한 잠금이 필요한 FULL 재작성을 반복하지 않는다. 수집 실패와 보관 실패는 숨기지 않으며 원래 장애 보고를 유지한다.
