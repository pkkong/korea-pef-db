# LP 출자공고 복원·정리 계획

작성: 2026-09-08. 2026-09-09 사용자 승인으로 1차 대조·10개 표본 검토를 시작했다. 운영 DB 변경·공개 배포는 이 단계에 포함하지 않는다.

## 목표와 범위

사용자가 공고 하나를 열면 어느 기관의 어떤 출자사업인지, 현재 단계와 마감일은 무엇인지,
그 판단을 어느 원문에서 확인할 수 있는지 알 수 있게 한다. 수집 건수는 완료 지표가 아니다.

1차 범위는 기존 공개 공고와 그 사업에 속한 최초 공고·정정·선정 결과다. 기존 목록 복원과
신규 공고 확장은 별도로 관리한다. 새 기관 확대, 전 자산군 백필, LP 프로필 재설계,
알림과 Vercel 이전은 이 복원 검수가 끝난 뒤 별도 작업으로 한다.
PE/VC/사모대출 등 기존 서비스 범위의 직접 출자·운용사 선정 공고를 우선한다.
기존 목록에 있는 일반 채권·주식 거래기관, OCIO, 용역·채용 등은 자동 승계하지 않고
각각 범위 밖 여부를 기록한다. 다른 자산군을 새로 포함하려면 범위를 먼저 정한다.

## 시작점: 확정 사실과 재확인할 사항

- 9월 7일 배포 조사에서는 공개 공고 카드 83개, legacy JSON 이벤트 103개였다.
  두 수치는 사업과 이벤트라는 단위가 달라 단순 차감으로 누락을 판단하지 않는다.
- 공개 카드 대표 원문 중 5개가 해당 JSON에 없었다. 원문 사이트에서 삭제됐다는 뜻은 아니다.
- 전체 검수 monitor/DB는 현 작업 공간에서 확보되지 않았다. 기존 HTML/JSON은 복원 단서이며
  검수 완료 원본으로 자동 인정하지 않는다.
- 공식 채널 목록의 parser_status와 실제 수집 코드 활성 상태가 일부 다르다.
  출처 신뢰성과 추출 정확도를 별도로 점검해야 한다.
- LP builder의 --monitor가 목록과 상세에 동일하게 전달되지 않는 구현도 복원 배포 전에 수정한다.

83개는 조사 당시 기준이다. 실제 복원 시작 시 공개 버전과 URL 목록을 고정해 기준 수를 다시 확인한다.

## 출처 채택 기준

| 출처 | 역할 | 공개 판단 |
| --- | --- | --- |
| 출자기관·공식 위탁 운영기관의 공고 상세와 원본 첨부 | 사업 조건·정정·선정 결과의 기준 | 게시 주체·문서·해당 사업의 일치를 확인한 뒤 채택 |
| 기관 공식 보도자료 | 선정 결과 등 명시된 사실 보완 | 공고와의 연결을 확인하며 지원 조건을 추정하지 않음 |
| 금융투자협회·벤처투자 관련 포털 등의 재게시 | 원본 발견과 누락 확인 | 원 발행기관과 문서 동일성 확인 전 자동 공개하지 않음 |
| 언론기사·검색 결과 | 공식 자료를 찾는 단서 | 단독으로 모집 상태·금액·최종 선정 확정 금지 |
| 기존 사이트·백업·CSV | 복원 대조 자료 | 과거 공개 사실만으로 검수 통과 처리 금지 |

공식 사이트도 일반 공지·홍보·용역 공고를 섞어 싣는다. 기관 이름이나 키워드만으로 채택하지 않는다.
위탁 운영기관은 LP와 별도 필드로 기록하며 누구를 대신해 공고했는지 근거를 남긴다.

공식 게시판 예시를 확인했다. 전체 출처 승인 목록은 1단계에서 확정한다.
- 국민연금 거래기관 선정공고: https://fund.nps.or.kr/impa/dlnginstslctnpbanclist/getOHEF0017M0.do
- 한국성장금융 출자사업공고: https://www.kgrowth.or.kr/notice.asp

## 공고를 정리하는 단위

`출자기관 → 출자사업(연도·회차·자산군·분야) → 개별 공고·정정·선정 결과 → 원문·첨부`

- 같은 사업은 목록에서 한 번만 보여주고 공고·정정·서류심사·최종 결과를 그 안에 모은다.
- 제목이 비슷해도 기관·연도·회차·분야가 다르면 합치지 않는다. 공식 참조번호와 본문의
  이전 공고 연결을 우선하며, 불분명한 묶음은 자동 확정하지 않는다.
- 같은 공고가 여러 곳에 재게시되면 사건은 하나, 출처는 여러 개로 보관한다.
- 한 공고가 여러 분야를 모집하면 공고문은 공유하되 서로 다른 마감·배정액·선정 결과는
  분야별로 구분한다. 상위 사업 총액과 분야 금액을 중복 합산하지 않는다.
- 정정은 해당 조건만 변경한다. 예를 들어 첨부 양식 수정만으로 선정완료가 모집중으로
  되돌아가면 안 된다. 재공고·취소 뒤 재개는 공식 문서가 확인될 때만 반영한다.

원문 제목은 그대로 보존하고 화면 제목을 별도로 정리한다. 화면 제목은
`기관 · 연도 · 사업명 · 회차/분야`를 기본으로 하되 원문에 없는 말을 만들어 넣지 않는다.

## 사실과 원 링크 연결

각 사업의 기관·분야·마감일·출자액·선정 GP는 근거 문서 ID와 해당 문장 또는 첨부 쪽수를 연결한다.
원문 URL, 최종 도착 URL, 게시판 글 번호, 게시일, 수집·마지막 확인 시각, 첨부 파일명과
내용 해시를 보관한다. URL의 글 번호 등 식별 매개변수를 임의로 제거하지 않는다.

공개 상세에는 `최초 공고`, `변경 공고`, `선정 결과`, `첨부파일`처럼 목적이 명확한
링크를 표시한다. 기관 홈페이지나 검색 결과를 공고 원문인 것처럼 연결하지 않는다.
세션형 링크라 직접 연결이 불안정하면 공식 게시판과 글 제목·번호를 함께 제공한다.

접속 성공 여부와 문서 일치 여부를 모두 검사한다. 200 응답의 로그인·오류 페이지를
정상 링크로 보지 않는다. 원문 삭제·차단·일시 장애는 구분하며 링크 변경 이력을 남긴다.
원문이 없어졌어도 과거 증거는 삭제하지 않는다. 확인 가능한 공식 대체 문서가 없으면
현재 공고 목록에서 제외하고 복원 보류로 관리한다. 보존본의 공개 제공은 별도 검토한다.

금액은 총 사업 규모·이번 출자 예정액·운용사별 배정액·목표 결성액을 구분한다.
없거나 충돌하는 금액은 추정하지 않는다. 선정 GP는 공식 결과의 이름을 먼저 보존하고,
프로필 연결은 동일 회사가 확인될 때만 한다.

## 화면 정리 원칙

목록은 한 사업당 한 줄에 가까운 평평한 공고 행으로 구성한다. 기본 정보는 기관·사업명·상태·마감일이며,
확인된 이번 출자액만 보조로 둔다. 검색과 기관·상태·자산군 필터만 우선 제공한다.
큰 통계 카드, 반복 배지, 자동 작성 장문 요약, 수집·검수 상태 표시는 넣지 않는다.

상세는 핵심 조건 → 진행 이력 → 원문·첨부 순서다. 목록의 제목 클릭은 상세로,
원문 버튼은 공식 상세 공고로 간다. 빠진 선택 정보는 빈 칸을 채우기 위해 추측하지 않는다.
마감일이나 현재 접수 가능성을 확인하지 못하면 모집중으로 표시하지 않는다.
`마감일 미기재`처럼 사용자 판단에 필요한 사실만 간결하게 표시한다.

## 실행 순서와 단계별 완료 조건

### 1. 기준 목록과 출처 목록 확정

기존 공개본을 읽기 전용으로 보존하고 모든 카드·상세 URL·원문·첨부를 목록화한다.
83개와 103개를 게시물 ID·원문 URL·연도·회차로 대조한다. 기존 항목마다
복원 확인 / 다른 사업에 병합 / 범위 밖 / 원문 확인 보류 중 하나와 이유를 기록한다.
기관별 공식 게시판, 운영 주체, 직접 링크 방식, 추출 상태, 마지막 점검일을 확정한다.

완료 조건: 기준 목록 전부에 대조 결과가 있고, 빠진 5개 대표 원문은 각각 탐색 경로와
결과가 기록돼야 한다. 다시 83개를 채우는 것을 목표로 하지 않는다.
산출물: 원문 대조표, 승인할 출처 목록, 복원 불가·불확실 항목 목록.

### 2. 작은 표본으로 정리 기준 검증

제안 표본은 2~3개 기관의 10개 사업이다. 최초 공고만 있는 경우, 정정, 선정 결과,
복수 분야, 중복 게시, 원문 누락 사례를 포함한다. 기관은 국민연금·한국성장금융과
기존 누락이 있는 기관을 후보로 삼고 1단계 접근·자료 확인 결과에 따라 확정한다.
각 사업의 원문과 핵심 조건을 대조하고 목록·상세 미리보기를 만든다.

완료 조건: 공개하는 핵심 값마다 근거가 있고 잘못된 사업 병합·마감 상태·금액이 없어야 한다.
사용자에게는 대조표 전체 대신 정리된 공고 10개와 화면 예시를 보여준다.
이 표본 검토가 끝나기 전 전체 복원이나 자동 공개로 확대하지 않는다.

### 3. 기존 목록 복원과 분리 검수

검증된 출처별로 묶어 나머지 기존 사업을 복원한다. 복원 담당과 별도 검증 담당이
마감일·금액·최종 선정·사업 병합·원 링크를 대조한다. AI 추출은 초안이며 근거 없는
보완은 금지한다. 불확실한 항목은 공개 자료와 분리한다.

완료 조건: 기준 항목 100%의 처리 결과 기록, 새 공개 대상 100%의 근거 연결,
모집중인 항목 100%의 유효 접수 근거, 잘못된 중복·필수 링크 누락·미해결 핵심 충돌 0건.
기존 상세 URL은 유지하거나 같은 사업의 새 URL로 연결하고 누락·병합 이유를 남긴다.

### 4. 재현 가능한 저장·배포와 이후 운영

수집 원문, 정리한 사업/이벤트, 검수된 공개본을 분리해 Supabase에 보관한다.
GitHub는 코드·출처 설정·검수 규칙을 관리하고 로컬 DB나 공개 HTML을 운영 원본으로 두지 않는다.
공개 링크는 공식 원문을 유지하며 원문 보존본은 비공개 근거로 관리한다.
목록·상세·공개 JSON을 같은 승인 자료로 만들고 별도 임시 환경에서 먼저 확인한다.

완료 조건: 빈 입력이 기존 공고를 지우지 않음, 실패 시 이전 공개본 유지,
전체 URL 대조·모바일 화면 확인, 공개 변경 내역 검토 후 배포.
Vercel 이전은 이 자료를 이용하는 별도 배포 작업으로 구분한다.

운영 제안: 모집중·최근 변경 사업은 매일, 과거 선정 결과는 낮은 주기로 재확인한다.
변경된 마감·금액·결과는 재검수하고 출처 장애는 새 자료로 덮지 않는다. 이 주기는 실행
계획의 제안이며 이번에 자동 수집이나 알림을 설정하는 것은 아니다.

## 역할과 다음 판단 지점

- Lead: 범위·출처 승인 기준, 표본 선정, 최종 공개 판단과 사용자 설명.
- LP Worker: 승인된 출처의 원문 확보·대조·정리. 검수 상태나 다른 서비스 자료를 임의 변경하지 않음.
- Verifier: 원문과의 일치, 중복·상태·링크·기존 URL 보존 점검. Worker와 같은 결과를 독립 대조.

실행 시에만 작은 역할 팀을 구성한다. 현재는 기준과 계획 문서만 작성한다.
첫 실행 목표는 전체 크롤링이 아니라 **기준 목록 대조표와 10개 사업의 정리 표본**이다.
작업량·예상 일정은 1단계에서 실제 원문 접근과 누락 정도를 확인한 뒤 산정한다.
