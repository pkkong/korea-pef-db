## 공개 범위와 사업 판정

### LP 공고 복원 품질 원칙 (2026-09-08)

- 복원은 기존 화면 숫자나 수집 건수 복구가 아니라 공식 근거에 연결된 사업 이력 재구성이다.
- 출처 신뢰성, 추출 정확도, 검수 통과 여부를 분리한다. 공식 도메인이나 기존 공개 기록만으로 승인하지 않는다.
- 사업별 공고·정정·선정 결과를 한곳에 묶고 핵심 사실을 해당 원문·첨부에 연결한다.
- 누락과 불확실성을 숨기기 위해 추정하거나 중복 행으로 수를 채우지 않는다.
- 목록은 기관·사업명·상태·마감 중심으로 간결하게 유지하고 상세에서 이력과 원문을 제공한다.
- 복원 작업은 `docs/history/notes/lp_notice_restoration_plan_2026-09-08.md`의 대조표와 10개 표본 검토부터 시작한다.

- 2026-09-10 표본 대조에서 확인: 공고번호의 `1호/3호`는 사업 회차로 자동 변환하지 않는다. 게시판 이전·다음 글은 본문 추출에서 제외한다.
- HWP 변경 기록과 숨은 텍스트 때문에 수정 전후 금액이 붙어 나올 수 있다. 숫자가 충돌하면 최종 표시 문서의 직접 검수 전까지 금액·분야 확정을 보류한다.
- HTTP 200이라도 오류 문구가 나타나면 원문 확인 실패다. 과거 마감일 경과는 최종 선정 완료의 근거가 아니다.

### 2026-09-10 LP 기본 명단 우선 원칙

사용자 결정으로 공고 복원에 앞서 법적 유형별 LP 명단을 정리한다. 이전의 공고이력 0건 제외 및
OCIO 기본명단 제외 규칙은 새 기본 명단에 적용하지 않는다. 운영 공개 화면 설정은 별도 전환 전까지 유지한다.
참여 자격·실제 출자활동·기금관리/운용 역할·공개 상태를 분리한다. 기관과 자금은 별개 주체로 관리하며,
공고 운영기관을 실제 출자자로 자동 치환하지 않는다. 검토본과 현재 운영 입력을 혼동하지 않는다.
상세 기준은 `docs/history/notes/lp_directory_basis_2026-09-10.md`, 검토 데이터는 `data/lp_directory_review.json`이다.

### LP 공고 수집 우선순위 (2026-09-12 사용자 결정)

산업·기업·수출입은행, 공제회·연기금 전체를 우선 조사한다. 일반은행·보험은 이번 수집 범위에서 제외하고 기타 기관은 보류한다. 기본명단 삭제나 법적 부적격 판단을 뜻하지 않는다. 업종 분류와 법적 자격 경로, 공개모집 여부·빈도는 각각 관리한다. 연금과 기타 법정기금, 공제회와 협동조합 중앙회를 구분한다. PE 공고 집계 사이트는 누락 기관 발견용으로 활용하며 공식 원문 연결·확인 상태를 별도 기록한다. 정정·연장·선정결과를 독립 모집건으로 중복 집계하지 않는다.

### LP 관리 명단 범위 정정 (2026-09-13 사용자 지시)

한국성장금융·우정사업본부·한국자산관리공사와 신협·새마을금고·농협·수협·산림조합 중앙회를 우선 관리 대상으로 포함한다. 이전 기타기관 일괄 보류보다 우선한다. 법적 자격 후보 전체를 공고 관리 기본 화면에 노출하지 않는다. 일반 법정기금을 연기금으로 일괄 우선 지정하지 않는다. 연금기관, 공제사업 기관, 지정 은행·중앙회·기관 및 PE 공고가 발견된 고용·산재보험기금을 합쳐 현재 24개를 기본 화면에 표시한다. 나머지 109개는 참고 명단에 보존한다. 법정기금 추가는 PE 모집 관련성을 확인한 후 결정한다. 운영 사이트에는 아직 적용하지 않은 로컬 검토본이다.

### LP 자료 유형과 작업 우선순위 — 2026-10-24

- 미판독 첨부·대조 후보의 개수를 곧바로 다음 작업량으로 발표하지 않는다. 먼저 모집 공고/후속 결과/FAQ/제출서식/기업 안내와 현재 범위의 관련성을 구분한다.
- 사용자는 제안서 양식 수집·다운로드 제공을 원하지 않는다. 모집 원문·일정·규모·목적과 후속 공고 연결을 먼저 처리한다. 이미 별도 공식 HWP/PDF를 읽은 공고의 서식 ZIP은 판독 건수를 늘리려고 펼치지 않는다.
- 보관 문서 증가와 공개 PE 사업 증가를 구분하고, 새 공고ID/인공지능 수동 선별로 채우지 않는다. 대조와 공식 목록 탐색으로 발견한 자료만 현재 검증 경로로 처리한다.

### 공식 목록 상태표시와 제목 근거 — 2026-11-06

- 공식목록의새글/배지접근성문구를공고제목에섞지않는다. 관측한상태표시DOM만제외하고실제제목문자열·중첩텍스트·이미지대체텍스트는보존한다. 단어를전역삭제하거나일반제목대조를느슨하게하지않는다.

## 공개 화면과 상세

### LP 사업 상세의 완료 기준 (2026-09-14 사용자 반복 지적 반영)

자료가 연결된 화면만으로 서비스 완성을 주장하지 않는다. 한 사업의 공식 첨부까지 읽고 출자규모·리그별 조건·지원제한·제출방법·심사 예정과 실제 경과를 구분해야 한다. 확인 가능한 첨부를 읽지 않은 채 미확인 문구로 채우지 않는다. 첫 화면은 핵심 조건을 비교할 수 있어야 하며 계산은 근거 수치에서 파생하고 법적 자격/출자비율 상한 판단으로 오인시키지 않는다. 사용자 지정 기존 Vercel 운영 구조를 유지하고 이 한건 개선을 이유로 별도 Sites 제품을 만들거나 호스팅을 전환하지 않는다.

### 공개 문구 (2026-09-14 사용자 지적)

공개 화면에 ‘자료 확인 기준’, ‘최근 확인 이력’, 불필요한 ‘한국시간 기준’, ‘이 화면은’, ‘현재 확인된 것’ 등 작업자·생성 과정의 말투를 쓰지 않는다. 날짜는 공고일·마감일·선정일처럼 사건명으로 표시한다. 검수일·추출방법은 내부 데이터에 보존하고 기본 화면에 노출하지 않는다. 불확실한 결과는 ‘결과 미확인’처럼 짧고 정확하게 표시하며 ‘미발표’로 단정하지 않는다. 단순 화면 설명·자기평가·장황한 면책 문구를 추가하지 않는다.

### LP 상세 정보 밀도 (2026-09-15)

일반 자격(국내 사무소·법상 GP 자격 등), 제출방법·배송·주소, 공고 내용을 다시 설명하는 문단은 기본 상세에서 제외한다. 출자 규모·리그별 비교·중요 제한·일정·선정결과·원문 중심으로 표시한다. 상세 증거는 내부 자료에 보존한다. 항목을 무조건 늘리거나 공고 전문을 화면으로 옮기지 않는다.

### LP 공통 상세 확정 (2026-09-15 사용자 지시)

상세 순서는 진행 일정 → 모집 개요/리그 → 선정 GP. 주요 제한·출자/운용조건·제안서양식·다운로드목록은 기본화면에 넣지 않는다. 출자공고 원문과 일정/결과의 근거링크만 남긴다. 기관별 전용renderer를 만들지 않으며 공통 프로그램·이벤트·리그·선정관계 데이터로 같은 코드를 사용한다. 예정은 완료와 구분한다.

- LP 모집 개요에는 공고에서 확인된 주목적(투자대상·의무투자 비중)을 포함한다. `primary_investment`에 문구와 근거를 저장하며 일반 GP자격·운용조건과 구분한다. 미확인 주목적은 추정하지 않는다.

- LP 주목적은 공식 투자대상·의무비율만 요약한다. 비율의 분모(펀드 약정총액/LP 약정액/의무투자액)를 구분하고, 확인되지 않은 주목적을 투자 분야로 대체하지 않는다. 동일 공고의 블라인드·프로젝트 모집은 선정 범위를 구분한다. 모바일 일정은 날짜 위/내용 아래로 읽히도록 배치한다.

- LP 일정은 공통 단계와 원문 단계명, 날짜 정밀도, 예정/공고상 마감/실제 결과, 출처를 별도 저장한다. 날짜 경과만으로 심사 착수·선정 완료를 추정하지 않는다. 교직원공제회 한 건에 schedule_stages로 먼저 적용했다.

- LP 샘플은 뉴스레터 공통 service.css의 색상 토큰·하단 메뉴 아이콘을 공유한다. 모바일 리그 표는 항목명/값의 세로 행으로 표시하고 가로스크롤을 요구하지 않는다. 320/390/768/1280px에서 자식 요소 경계까지 검사해 overflow 숨김으로 문제를 가리지 않는다.

- LP 진행일정은 모바일에서도 날짜/진행내용 두 열의 간결한 행으로 표시한다. 세로 적층으로 과도하게 늘이지 않는다. 상단 공고→접수→심사→선정 흐름은 균등 간격·가벼운 구분선으로 유지한다.

- LP 목록 검수는 상세 검수로 대신할 수 없다. 사용자 제공 모바일 화면처럼 공고2개로 화면이 차는 큰 여백·반복미확인문구를 금지한다. 목록은 기관/상태, 짧은사업명, 출자액/일정3줄이며 행높이390px기준약100px. 실제 목록 스크린샷·검색복원·자식경계검사를 배포 전에 확인한다.

- LP 검토 화면은 현재 로그인 불필요(사용자 지시). 우선 공식공고 읽기·비교만 제공하고, 수정/공개 반영은 대화로 처리한다. 계정 등록을 이용의 선행조건으로 다시 요구하지 않는다.

### LP 공개 마무리·예약 실행 경계 — 2026-10-26

- 사용자 빠른 출시 지시를 반영해, 이미 검증한 공개 앱의 검색 설정을 새 예약 이벤트 생성까지 무기한 미루지 않는다. 공개 앱 배포·수동 전체 수집·실제 예약 성공은 별도 사실로 기록한다. 예약 active나 수동 성공을 실제 예약 성공으로 표현하지 않는다. 예약·실패 알림은 유지한다.
- 공개 성공 페이지만 index/follow를 허용한다. 검토의 두 경로와404/503/405/health는noindex, 검토는no-store/no-referrer/frame-deny를 유지한다. robots는DB나다른서비스 없이 응답한다. 배포 후 실제 응답 검사를 통과해야 공개 설정 완료라 기록한다.
- 교직원 수집은 우정/수출입과 같은 별도macOS job에서 수행하고 같은 실행의2시간 이내 artifact를 publisher에서 원문 기준으로 재판독한다. collector가 준비한 programs를 신뢰하지 않는다. 누락·오래된 artifact는 실패로 남겨 기존 자료를 보존한다.
- 자체 게시판 수집기가 맡은 기관을 협회 역탐색에서 중복 요청하지 않는다. 위임한 기관을 coverage에 기록하고 자체 수집의 오류/아티팩트 누락을 최종 장애 보고로 유지한다. 기존 보류를 삭제하거나 읽기전용 역탐색의 기본 동작을 끄지 않는다. 신규 기관 중 자체 수집 미연결 경로는 기존 역탐색을 계속한다.
- 기관 목록/본문 실패 후 재시도는 정상기관을 반복하지 않고 실패기관 최대2곳을 각각새세션으로1회만 수행한다. 첨부 한도·탐색깊이 오류를 반복하지 않는다. 첫 보류·커버리지·시각은 retry_history에 보존하며 마지막도 실패하면 오류를 남긴다. 복구 workflow의 retry_failed_institutions=true도 같은 함수를 사용하며 현재등록 기관만 대상이다.
- 게시판 형식 변경은 실패 응답 원문에서 확인한 구/신 구조만 지원하고 게시판·검색·행·날짜·페이지 검증은 유지한다. 총회연금의 표 이름 변경을 빈 목록/일시 장애로 넘기거나 고정 공고ID로 우회하지 않는다.
- 공식 사이트가 점검 안내 주소로 이동한 뒤 실패하면 최종 공식주소·HTTP상태·원오류를 보존한다. 같은 실행의 반복 검색/재시도를 중단하고 이전 정상 자료를 유지한다. 다음 정기 실행은 다시 확인하며 점검을 영구 제외하거나 전체 정상으로 바꾸지 않는다.
- 공개 상태 JSON은 UTF8·compact·유한 숫자로 DB 쓰기 전에 직렬화하고 바이트 수/단계 소요시간만 기록한다. 발행 잠금20초·쿼리120초·트랜잭션 유휴300초 제한은 SET LOCAL로 적용해 원문과 공개 상태의 같은 트랜잭션을 유지한다. 수동 복구는 최신 실패 실행 자료를 사용하고 새 예약과 충돌할 오래된 복구를 중복 실행하지 않는다. 실제 예약 실패와 수동 발행 복구는 별도 기록한다.

## 공식 사이트 접속과 전송

### LP 공식 접속 오류 대응

간헐적인 DNS 조회 실패가 여러 기관에서 나오면 기관별 예외를 계속 추가하기 전에 공통 전송 경로를 확인한다. `lp_transport_errors.transient_dns`는 실제 resolver 예외만 분류하며 오류 문자열을 근거로 성공 처리하지 않는다. 협회 수집은 기존 3시도/추가4회 예산, 새 기관 세션은 기존 2시도, 기관 원문 공통 수신은 DNS에만 최대3시도를 적용한다. KFINCO는 단일 수신 함수를 사용해 자체 3시도/추가4회 예산과 중첩하지 않는다. TLS·호스트·본문 검증은 완화하지 않고 소진된 오류는 기존 자료를 보존한 뒤 보고한다. 발행 성공과 마지막 장애 보고 성공을 구분하며 두 결과를 현황 문서에 함께 기록한다.

금투협 판독 오류는 먼저 실제 수신 길이·HTML 종료·잘린 멀티바이트 위치를 확인한다. 2026-10-20 동일 요청의 HTTP/1.0 curl 응답은 32,120바이트에서 두 번 잘렸지만 종료 코드가0이었고, HTTP/1.1 curl은50,965바이트의 완전한 원문을 받았다. 현재 복구 경로는 `--http1.1`이며 종료 코드만으로 성공을 선언하지 않는다. 엄격한 문자·HTML 검사와 크기/TLS 검증을 유지한다. 추가 원문이나 판독 결과를 코드에 고정해 넣지 않는다.

### LP 누락 대조와 지역 전송 — 2026-10-21

- 벤치마킹 사이트의 감지 목록은 수집 누락 후보를 찾는 보조 자료다. 제목·기관·링크·감지 시각만 비교하고 금액·마감·결과·첨부 내용은 공개 근거로 가져오지 않는다. 자체 PDF 파일명으로 공식 원문 URL을 추정하지 않는다.
- 감지 시각과 원공고 게시일, API 응답 시각과 실제 수집 시각, 브라우저 갱신 주기와 서버 수집 주기는 서로 다르다. 공개 코드에서 확인한 사실과 내부 운영 방식에 대한 추측을 구분한다.
- 공개 사업 목록에 없다는 이유만으로 미수집으로 세지 않는다. 운영 DB에 보존한 공식 문서의 기관·제목·원문 주소까지 읽기 전용으로 대조한다. 후보 수는 누락된 PE 사업 수가 아니다.
- 새마을금고 GitHub 경로의 HTTP400 Request Blocked에 한해 서울 전송기를 한 번 사용한다. 인증서 검증·응답 크기·해시·공식 경로 제한과 기존 원문 판독을 유지한다. 다른 기관의 오류를 이 전송기로 일괄 우회하지 않는다.
- 수동 운영 검증 성공, 이후 예약 실행 성공, 첫 공개 완료는 각각 증거를 기록한다. 다음 작업 범위를 끝없이 늘려 출시 기준을 바꾸지 않는다.

### LP DNS 장애 보완 검증 — 2026-10-21

같은 공식 호스트가 로컬/다른 실행에서 정상이라고 해서 과거 DNS 장애 원인이 해결됐다고 표시하지 않는다. 신협과 산업은행의 macOS DNS 오류를 관측해 직접 기관 수집 Session에 공통 IPv4 복구를 적용한다. typed DNS 오류 때만 기존 두 번째 직접 시도를 바꾸며, 다른 HTTP/TLS/본문 오류의 게이트를 낮추지 않는다. 신협은 검증된 native 경로, 다른 직접 기관은 동일한 쿠키·redirect 정책의 IPv4 HTTPS 연결을 쓴다. 고정 IP·제3자 프록시·TLS 완화·무한 재시도를 추가하지 않는다. KFCC의 기존 서울 전송이 결합될 수 있으므로 전체 요청 2회가 아니라 직접 시도 2회라고 설명한다. 오류 주입 시험, 주입 없는 실제 수집, 이후 예약 성공을 구분해 기록한다. 실패 시 기존 자료를 보존하고 장애를 알린다.

공식 사이트를 실제로 호출하는 전송 시험·오류 주입 수집·운영 수집은 같은 `lp-program-collection` 동시 실행 제한을 사용한다. 같은 기관을 호출하는 시험과 운영을 병렬로 실행하지 않는다. 외부 사이트에 접속하지 않는 코드 검토와 fixture 검사는 독립적으로 병렬 진행할 수 있다. 동시 실행 시점의 오류가 단독 시험에서 사라져도 부하가 원인이라고 단정하지 않는다.

### 전문건설공제조합 서울 전송·인증서 규칙 — 2026-10-23

- 전문건설공제조합은 운영 macOS에서 확인한1414바이트 HTTP400의 두 문구·정확 공식 URL·비밀 토큰 존재 때만 인증된 서울 전송기를1회 사용한다. 일반400·404·TLS 오류를 일괄 우회하거나 실패를 빈 목록으로 바꾸지 않는다. 원문/첨부는 기존 목록·본문 근거와 해시 검증으로 판독한다. 공고ID 허용목록을 만들지 않는다.
- 서버가 빠뜨린 Sectigo 중간 인증서1장만 공식 배포본 DER지문으로 고정하고 Node 기존루트에 연결한다. 파일 전체를 신뢰하지 않고 정확히1장만 허용·검사한 인증서만 사용한다. 루트 추가·TRUSTED CERTIFICATE·partial-chain·호스트명/TLS 검증 해제는 금지한다. 만료/발급자 변경은 눈에 보이는 수집 실패로 남긴다.
- 서울 전송기 배포의 실제 목록 검증도 `lp-program-collection` 대기열을 공유한다. 임시 진단 프로젝트는 항상 삭제하며, 진단/배포의 목록200과 전체 수집/발행 성공은 각각 증거를 기록한다. 수동 성공과 이후 예약 성공도 구분한다.

### 신협 두 DNS 실패 이후 서울 복구 — 2026-10-23

- 신협은 첫 직접 요청의 DNS 오류 뒤 두 번째 native curl도 exit6으로 실패했을 때만 인증된 서울 전송을 한 번 허용한다. `CuDnsError`로 구분하며 오류 문자열만으로 선택하지 않는다. 토큰이 없거나 다른 curl·TLS·HTTP·본문 오류이면 기존 실패를 유지한다. 요청 한도는 직접 2회와 조건부 서울 1회다.
- 서울 전송은 공식 게시판 1020, 메뉴 100007, 설정한 두 검색어, 관측한 상세 번호와 32자리 첨부키만 허용한다. 지역·해시·3MiB 한도·기본 TLS·호스트명 검증·리디렉션 금지를 유지한다. 직접 경로의 12MiB 한도는 변경하지 않는다.
- 두 DNS 오류 주입 시험에서도 실제 서울 본문과 PDF 텍스트를 받아 기존 출처 검증을 통과해야 한다. 다운로드 건수만으로 판독 성공을 주장하지 않는다. 시험, 일반 운영, 이후 예약 결과를 구분한다. 실제 공식 요청은 `lp-program-collection` 대기열을 공유한다.

### 산업은행 DNS 보완 및 벤치마크 식별 — 2026-10-24

- 산업은행 두 번째 AF_INET 조회까지 typed DNS 오류일 때만 정확한 www.kdb.co.kr:443의 A레코드를 고정 HTTPS DNS 주소에서 한 번 조회한다. 원 공고 HTTP 요청을 새 전송기로 옮기지 않는다. 원래 HTTPS 호스트/SNI·인증서·쿠키·OfficialRedirect와 두 직접 시도를 유지한다. 공인 IPv4·질문·CNAME 연결 검증, DNS5초/16KiB, 재시도0과 리디렉션 금지를 지킨다. 고정 원서버IP·임의 CA·실패 응답의 빈 목록 처리는 금지한다.
- DNS에 소비한 시간은 연결 시간에서 차감한다. 주소는 요청 안에서만 사용하며 DNSSEC AD=false만으로 정상 미서명 도메인을 거절하거나 DNSSEC 검증 완료라고 주장하지 않는다. DNS 주입 시험과 자연 발생 복구, 일반 운영, 이후 예약을 구분한다.
- 벤치마크의 기관 식별은 수집 정책과 분리한다. CSV의 정확 기관명/저장 별칭만 쓰며 대상 밖 기관은 식별 후에도 별도 보류한다. 대상 내/밖 동명이름은 모호함으로 남긴다. 협회·OCIO·GP 제목에서 LP를 차용하지 않는다. 식별 개선 건수를 새 공고 확보나 PE 누락 해소로 계산하지 않는다.
- 최근1년 국내 PE 작업은 docs/lp_collection_delivery_plan.md의 묶음으로 진행한다. 추정 작업량은 10월24일 기준으로 관리하며, 단일 장애 보완만 반복해 데이터 대조와 수집 연결이 무기한 밀리지 않도록 독립 작업을 병행한다.

### LP 빈 공고·제한 행·큰 자료 전송 — 2026-10-30

- 완성된 공식 공고 양식에서 제목·날짜·본문·첨부가 모두 빈 경우만 건별 보류한다. 과거 근거는 보존하고 다음 실행에서 재확인한다. 잘린 응답·일부 필드 누락·차단 안내를 같은 정상 보류로 묶지 않는다. 관측한 특정 공고ID를 코드에서 제외하지 않는다.
- 공식 API의 정확한 정수 closed=1은 제한 행으로 남기고 다른 공개 행을 계속 처리한다. 제한 상세/첨부를 요청하지 않으며 목록 보관본에도 식별자와 제한 플래그만 남긴다. 플래그 형식 오류와 공개자료의 실제 오류는 실패로 보고한다.
- 누적 상태의 과거 증거를 현재 보고서와 같다고 가정해 제거하지 않는다. 손실 없는 압축·지문·완전 복원 대조를 쓰기 전에 완료하고, SQL 소비 필드는 읽을 수 있는 형태로 유지한다. writer를 되돌릴 때도 압축 decoder 호환을 보장한다.
- 큰 JSON 문서 저장은 executemany/pipeline을 사용하지 않는다. 크기와 행 수가 제한된 파라미터 SQL로 나누되 동일 트랜잭션을 유지한다. 뒤쪽 실패 시 문서·보고서·공개 상태가 모두 rollback되는지 실제 PostgreSQL에서 검증한다. TLS 검증을 낮추거나 무제한 재시도로 전송 오류를 숨기지 않는다.

### LP 총회연금재단 공고와 전체 발행 계약 — 2026-10-25

- 같은 연도·하반기·제목이어도 모집 원문 게시물이 다르면 다른 모집으로 둔다. 이미 공개 중이던 사업 연결이나 본문에 직접 연결된 원공고만 후속 단계 근거로 사용한다. 가까운 날짜와 GP 이름으로 연결하지 않는다.
- 자산군별 별도 제출이 확인된 PE 블라인드 트랙은 기본 공고를 발행할 수 있다. 혼합 전체500억원/1,000억원을 PE 배정액으로 복사하지 않으며 O개사를 숫자로 만들지 않는다. 제안서·실적 조건을 주목적으로 표시하지 않는다.
- DOCX/ZIP은 바이트·공식 파일명·본문을 재검증하고 헤더·각주·삭제/숨김 텍스트를 근거로 쓰지 않는다. 엑셀 제출서식은 수집하지 않는다.
- 수집/분류 단위검사 뒤 반드시 기존 선정GP의 원문 연결을 포함한 lp_program_service.validate 및 전체 페이지 생성까지 검증한 후 운영한다. PCK 호환 보정으로 다른 기관의 기존 일정이 바뀌지 않아야 한다. 기존 이벤트 명칭·주소·GP 연결을 유지한다.

### LP DB 연결 점유와 공유 인프라 장애 — 2026-10-27

- 원문 판독·출처 검증·페이지 생성 중 DB 연결/발행 잠금을 유지하지 않는다. 짧은 REPEATABLE READ READ ONLY 트랜잭션에서 기준 자료와 버전을 읽고 닫은 뒤 검증한다. 쓰기 연결은 READ COMMITTED로 유지하며 같은 발행 잠금 획득 후 별도 문장으로 run_id/updated_at/전체 검토 결정을 대조한다. 대기 중 변경이나 검토 수정·삭제가 있으면 첫 쓰기 전에 중단한다. 실제 원문/공개 상태 저장은 같은 트랜잭션으로 묶는다.
- 공유 DB 접근 장애는 개별 수집기 오류와 구분한다. 타 서비스의 동시 실패는 읽기 전용으로 증거만 확인하고 코드 결합·단일 원인·결제 필요를 단정하지 않는다. 공개503이 남으면 정상 운영으로 보고하지 않는다. 관리 권한이 없으면 정상 관리 로그인을 요청하고 비밀값을 채팅으로 요청하지 않는다.

### 관리 로그인 시도 순서 — 2026-10-27

- 관리자 로그인이 필요하면 먼저 기존 브라우저 세션과 정상 SSO 경로를 확인한다. 로그인 화면이 보인다는 이유만으로 바로 사용자에게 넘기지 않는다. 장치 잠금이나 추가 인증 때문에 진행할 수 없을 때만 필요한 조작을 구체적으로 요청한다. OS 잠금과 인증 절차를 우회하거나 비밀값을 채팅으로 요청하지 않는다.

### 인증 대기 후 상태 재확인·용량 경고 — 2026-10-27

- 인증 대기나 사용자 응답으로 시간이 경과했으면 작업을 재개할 때 현재 health/최신 실행을 먼저 확인한다. 이미 회복됐으면 과거 실패를 근거로 강제 재시작·연결 종료를 하지 않는다. 실제 예약 성공과 수동 복구, 변경 적용과 회복 관측을 각각 기록한다.
- 사용량 경고는 프로젝트별 한도와 실제 큰 테이블을 확인한다. 조직 합계만으로 결제 필요를 단정하지 않는다. 기존 근거자료를 옮기거나 줄이려면 비공개 원문 보존·검증·복원·현재 검토/발행 계약·실패 시 원자료 유지와 공간 회수 방식을 먼저 구체화한다. 한도 초과를 장애의 확정 원인으로 설명하지 않는다.

### LP 이력 용량과 원본 보존 — 2026-10-28

- 원문을 보존하는 비공개 이력 보관은 `scripts/archive_lp_collection_reports.py`와 `services/lp/src/lp_report_archive.py`로 실행한다. 원문 행 삭제·자료 손실·유료 전환으로 용량 문제를 숨기지 않는다.
- 최신3회와 현재 발행 실행을 보호하고 업로드·전체 복원 일치·익명 접근 차단 뒤 행 버전 검사로 치환한다. 첫 운영 적용은1건 실제 DB 복원까지 검증한 뒤 확대한다.
- 신뢰한 main의 정기 수집/복구 완료 후 별도 유지보수 작업에서 최대5건 보관·일반 VACUUM을 수행한다. 수집25분 제한에서 이력 보관 시간을 분리하고 PR/fork의 완료 이벤트는 받지 않는다. 수집 장애 신호는 유지한다. 강한 테이블 재작성은 별도 `reclaim`에서 전체 보관 검증·LP 잠금·크기/시간 제한 후 실행한다.
- DB 크기 조사는 `pg_column_size` 등 메타데이터를 사용한다. 전체 큰 JSON의 `octet_length(report::text)`를 한 쿼리로 계산해 DB를 오래 점유하지 않는다.
- Storage 오류는 HTTP 상태와 정해진 오류명만 기록한다. 실제 확인된 구형400/statusCode404/정확한 없는 객체 응답만 누락으로 해석하고 모든400·인증 실패를 없는 파일로 취급하지 않는다.
- 실제 저장량과 공개 상태는 실행 ID/시각을 붙여 `docs/lp_collection_status.md`에 기록한다. 위치 치환만으로 물리 DB 파일 크기가 줄었다고 보고하지 않는다.

자동 보관은 자체 대기열을 사용해 예약 수집의 pending 실행을 취소하지 않는다. 수동 점검/공간 회수는 기존LP 대기열을 유지한다. 치환 잠금과 행 버전 보호는 공통이며, 평상시 VACUUM은 발행 advisory 잠금을 잡지 않고 TRUNCATE FALSE로 실행한다. 쿼리 제한은180초·경합 잠금 대기는5초다. 수동 FULL 회수만180초를 허용한다.

### LP 대형 보고서 전송 실패 — 2026-10-30

- 쿼리 시간 제한은 클라이언트의 큰 파라미터 전송 정지를 모두 제한하지 못한다. 실제 실패 단계와 전송 바이트를 확인하고, 다른 실행 환경에서도 같은 현상이 있으면 OS 전환을 원인 해결로 설명하지 않는다.
- 전체 보고서의 필드를 없애거나 최신 보고서 reader 형식을 바꾸지 않고, 작은 UTF8 조각 전송과 서버 내 합치기로 저장한다. 임시 상태·보고서·문서·공개 화면이 같은 트랜잭션으로 원복되는지 실제 PostgreSQL에서 검증한다. 쿼리 제한 확대·무제한 재시도·부분 commit으로 실패를 숨기지 않는다.
