# Korea PEF Intelligence 비전공자용 시스템 개요

작성일: 2026-06-10

## 이 문서의 목적

이 문서는 코딩 비전공자가 이 서비스를 한 번에 이해할 수 있도록 만든
입문용 시스템 개요다.

이 서비스는 단순한 웹사이트가 아니다. 한국 PEF 시장 관련 자료를 모으고,
정리하고, 검토하고, 다시 공개 화면으로 내보내는 데이터 인텔리전스 서비스다.

전체 구조는 네 장의 투명 필름이 겹쳐진다고 보면 된다.

| 레이어 | 쉬운 표현 | 설명 |
| --- | --- | --- |
| 1. 서비스맵 | 사용자가 보는 지도 | 브리프, LP, GP 같은 제품 메뉴와 화면 구조 |
| 2. 데이터 흐름도 | 재료가 상품이 되는 과정 | FSS, 뉴스, LP 공고, CSV가 DB와 웹페이지로 바뀌는 흐름 |
| 3. DB 설계 | 서비스의 기억 장치 | GP, 펀드, LP, 뉴스, 인물 같은 정보가 연결되는 방식 |
| 4. 운영 워크플로우 | 매일 굴러가는 순서 | 수집, 검토, 빌드, 배포, 품질 확인의 반복 절차 |

이 네 레이어가 따로 놀면 단순 파일 모음이 되고, 서로 잘 겹치면 하나의 완성된 서비스가 된다.

## 한 문장 요약

Korea PEF Intelligence는 한국 PEF 시장의 GP, 펀드, LP, 뉴스, 인물, 실무 지식을 연결해
내부 운영자가 관리하고 외부 사용자가 읽을 수 있게 만드는 정적 웹 기반 데이터 서비스다.

## 1장. 서비스맵

서비스맵은 "사용자가 어디로 들어가서 무엇을 보는가"를 설명한다.

현재 공개 서비스의 중심 메뉴는 세 개다. Wiki는 나중에 다시 기획할 때까지
공개 메뉴와 매일 빌드에서 제외한다.

| 공개 메뉴 | 사용자가 알고 싶은 질문 | 현재 역할 |
| --- | --- | --- |
| 브리프 | 오늘 한국 PEF 시장에서 무슨 일이 있었나? | 매일 뉴스와 주요 시장 이벤트를 읽는 화면 |
| LP | 어떤 출자기관이 어떤 위탁운용사 선정이나 출자공고를 냈나? | LP 기관, 출자공고, 선정 GP, LP 프로필을 보는 화면 |
| GP | 이 운용사는 누구이고, 얼마나 크고, 어떤 펀드와 뉴스가 연결되어 있나? | GP 디렉토리와 GP 상세 프로필 |

공개 화면 밖에는 내부 운영자가 보는 콘솔이 있다.

| 구역 | 대상 사용자 | 역할 |
| --- | --- | --- |
| `services/newsletter/deploy/site/` | 외부 사용자 | GitHub Pages로 배포되는 공개 사이트 bundle |
| `services/newsletter/deploy/site/` | 외부 사용자 | GitHub Pages로 배포되는 공개 사이트 bundle |
| `dashboard/` | 내부 운영자 | DB 품질, 수집 상태, 작업 큐, 운영 지표 확인 |
| `exports/` | 운영자와 에이전트 | 검토용 CSV, 엑셀, 작업 목록 |
| `docs/` | 운영자와 개발자 | 제품 원칙, 설계, 운영 규칙 |

서비스맵을 그림으로 보면 다음과 같다.

```text
외부 사용자
   |
   |-- 브리프: 오늘의 뉴스와 시장 이벤트
   |-- LP: 출자기관, 출자공고, 선정 GP
   |-- GP: 운용사, 펀드, 인물, 관련 뉴스

내부 운영자
   |
   |-- dashboard: 품질 확인, 작업 큐, 운영 상태
   |-- exports: CSV/엑셀 검토
   |-- docs: 운영 규칙과 설계 기준
```

중요한 점은 공개 서비스와 내부 운영 콘솔이 분리되어 있다는 것이다. 공개 화면에는 운영자용 표현,
검토 대기, 작업 큐, 내부 품질 상태 같은 문구가 노출되지 않아야 한다.

## 2장. 데이터 흐름도

데이터 흐름도는 "원천자료가 어떤 과정을 거쳐 화면이 되는가"를 설명한다.

이 서비스의 원천자료는 크게 네 종류다.

| 원천자료 | 예시 | 들어오는 방식 |
| --- | --- | --- |
| FSS PEF 자료 | 금융감독원 분기별 PEF 현황 엑셀 | 다운로드, 등록, 파싱 |
| 뉴스 | 더벨, 딜사이트, 인베스트조선 등 | 뉴스 수집 스크립트와 수동 보정 |
| LP 공고 | 국민연금, 벤처투자종합포털 등 | 공식 공고 페이지 수집 |
| 수동 CSV | GP 별칭, LP 기관, 인물, 프로필 근거 | 사람이 관리하는 입력 파일 |

전체 흐름은 다음과 같다.

```text
1. 원천자료
   FSS 엑셀, 뉴스, LP 공고, 수동 CSV

2. 수집/정제
   Python 스크립트가 파일을 읽고 이름, 날짜, 금액, URL을 정리

3. 운영 DB
   db/private_equity.db에 정리된 데이터 저장

4. 산출물 생성
   exports/*.csv, dashboard/data/dashboard_data.json,
   public read model / deploy JSON 생성

5. 화면 생성
   services/newsletter/deploy/site/ 아래 정적 HTML/JSON bundle 생성

6. 배포
   GitHub Pages 또는 로컬 정적 사이트로 공개
```

서비스별 흐름은 조금 다르다.

| 서비스 영역 | 데이터 흐름 |
| --- | --- |
| FSS/Market/GP/Fund | FSS 엑셀 -> DB 적재 -> GP/펀드 마스터 생성 -> 분석 CSV -> 공개 bundle 데이터 |
| 뉴스레터 | 뉴스 수집 -> 관련성 분류 -> 리뷰 큐 -> 최종 브리프 -> 공개 뉴스레터 HTML |
| LP | LP 기관 CSV와 공식 공고 수집 -> LP 공고 DB -> 공고/기관 통계 -> 공개 LP 화면 |
| People | 인물 CSV 입력 -> 인물/역할/학력 DB -> GP 상세 화면과 연결 |
| Wiki | 재기획 전까지 루틴 빌드 제외. 필요할 때만 명시적으로 Wiki HTML 생성 |

가장 중요한 운영 원칙은 이것이다.

```text
수집이 끝났다고 공개 사이트가 자동으로 바뀌는 것은 아니다.
DB와 산출물을 다시 만들고, 공개 HTML/JSON을 빌드하고, 배포해야 화면이 바뀐다.
```

즉, 이 서비스는 실시간 웹앱이라기보다 "정기적으로 새로 찍어내는 정적 데이터 서비스"에 가깝다.

2026년 6월부터 공개 사이트 빌드는 서비스별로 나눠서 실행하고, 마지막에 하나로 합치는 구조를 기준으로 한다.

```text
뉴스레터 빌드 -> 오늘의 브리프 HTML 생성
LP 빌드       -> 출자기관, 출자공고, 선정결과 HTML 생성
GP 빌드       -> GP 목록, Market, GP 상세 HTML 생성
Wiki 빌드     -> 재기획 후 명시 실행할 때만 실무 문서 HTML 생성

통합 빌드     -> 위 결과물을 services/newsletter/deploy/site/에 모음
배포          -> GitHub Pages 공개 저장소로 복사해서 공개
```

그래서 LP 공고만 바뀐 날에는 LP 빌드만 다시 돌릴 수 있고, Wiki는 재기획 전까지 루틴에서 제외한다. 다만 사용자가 보는 공개 주소는 그대로 하나의 사이트다.

## 3장. DB 주요 엔티티

DB 설계는 "서비스가 무엇을 기억하고, 무엇끼리 연결하는가"를 설명한다.

비전공자 관점에서는 DB를 엄격한 엑셀 파일 묶음으로 보면 된다.

| DB 용어 | 쉬운 설명 |
| --- | --- |
| 테이블 | 엑셀 시트 하나 |
| 행 | 시트의 한 줄 기록 |
| 컬럼 | 시트의 항목 |
| ID | 각 기록의 고유번호 |
| 연결 | 한 시트의 기록이 다른 시트의 기록을 가리키는 것 |
| View | 자주 보는 보고서를 미리 만들어 둔 가상 표 |
| Schema | 어떤 시트와 컬럼이 있어야 하는지 정한 설계도 |

현재 중심 DB는 `db/private_equity.db`다.

주요 엔티티는 다음과 같다.

| 엔티티 | 쉬운 의미 | 주요 테이블 |
| --- | --- | --- |
| GP | PEF 운용사 | `gp_house`, `gp_profile`, `gp_identifier`, `gp_profile_source` |
| Fund | PEF 펀드 | `pef_fund`, `fund_master`, `fund_period_snapshot`, `fund_event` |
| Reporting Period | 기준 분기 | `reporting_period`, `source_document` |
| LP | 출자기관 | `lp_institution`, `lp_profile_fact` |
| LP Notice | 출자공고와 선정 이벤트 | `lp_commitment_notice`, `lp_notice_gp_link` |
| News | 뉴스 기사 | `news_document`, `news_tag`, `news_entity_link` |
| People | GP/LP 관련 인물 | `person`, `person_role`, `person_education`, `person_source` |
| Wiki | 실무 문서 | 현재는 별도 DB보다 코드/문서 기반 |
| Deal | 거래 정보 | 장기 확장 영역, 아직 본격 구축 전 |

엔티티끼리의 관계는 서비스의 핵심 가치다.

```text
GP
 |-- 여러 Fund를 운용
 |-- 여러 People과 연결
 |-- 여러 News와 연결
 |-- 여러 LP Notice의 선정 GP로 연결

Fund
 |-- 특정 GP와 연결
 |-- 분기별 FSS snapshot을 가짐
 |-- 설립, 청산, 금액 변화 이벤트를 가짐

LP
 |-- 여러 출자공고를 냄
 |-- 출자공고 안에서 여러 GP를 선정
 |-- 뉴스와 연결될 수 있음

News
 |-- GP, LP, Fund, People 같은 엔티티와 연결
 |-- 공개 브리프가 되기도 하고 DB 업데이트 신호가 되기도 함

People
 |-- 특정 GP의 현재/과거 역할과 연결
 |-- 뉴스, 출처, 학력, 경력 정보와 연결
```

이 구조에서 중요한 원칙은 "이름보다 ID가 중요하다"는 것이다.

예를 들어 같은 운용사가 기사에서는 약칭으로 나오고, FSS 자료에서는 다른 표기로 나오고,
공식 홈페이지에서는 법인명으로 나올 수 있다. 그래서 화면에는 사람이 읽기 좋은 이름을 보여주되,
DB 내부에서는 안정적인 ID와 별칭 규칙으로 연결해야 한다.

또 하나의 중요한 원칙은 "출처가 없는 사실은 확정값으로 넣지 않는다"는 것이다.

이 서비스는 비어 있는 칸을 추정으로 채우기보다, 출처가 있는 값과 검토가 필요한 값을 구분하는 방향으로 설계되어 있다.

## 4장. 운영 워크플로우

운영 워크플로우는 "매일 또는 주기적으로 어떤 순서로 서비스를 굴리는가"를 설명한다.

크게 보면 네 가지 반복 업무가 있다.

| 업무 | 주기 | 목적 |
| --- | --- | --- |
| 뉴스레터 운영 | 매일 | 오늘의 PEF 뉴스 수집, 검토, 발행 |
| LP 공고 모니터링 | 하루 여러 번 또는 정기 | 신규 출자공고와 선정 결과 추적 |
| FSS/시장 데이터 갱신 | 분기 또는 필요 시 | GP, 펀드, 시장 규모 데이터 갱신 |
| 프로필/품질 보강 | 수시 | GP, LP, People, 출처, 별칭 품질 개선 |

뉴스레터의 기본 운영 흐름은 다음과 같다.

```text
뉴스 수집
   ↓
관련성 분류와 GP/LP 태깅
   ↓
리뷰 큐 생성
   ↓
운영자가 포함/제외와 섹션 검토
   ↓
최종 브리프 생성
   ↓
정적 HTML 빌드
   ↓
GitHub Pages 배포
```

LP 공고의 기본 운영 흐름은 다음과 같다.

```text
LP 기관/공식 채널 목록 확인
   ↓
공식 공고와 뉴스 후보 수집
   ↓
사업명, 마감일, 금액, 선정 GP 정규화
   ↓
DB 저장과 중복 제거
   ↓
공개 가능한 공고만 public 데이터로 내보내기
   ↓
LP 화면 빌드
```

FSS/GP/Fund 데이터의 기본 운영 흐름은 다음과 같다.

```text
FSS 분기별 PEF 자료 확보
   ↓
원천 파일 등록
   ↓
DB 적재
   ↓
GP 이름과 펀드 이름 정규화
   ↓
GP 마스터와 펀드 마스터 생성
   ↓
분기별 약정액 기준 지표와 품질 리포트 생성
   ↓
dashboard/공개 bundle 데이터 재생성
```

People/프로필 보강 흐름은 다음과 같다.

```text
뉴스나 공식 사이트에서 보강 필요 신호 발견
   ↓
CSV 또는 evidence 파일에 출처와 함께 입력
   ↓
DB에 반영
   ↓
GP/People 관련 export 생성
   ↓
공개 GP 상세 화면에 연결
```

운영자는 보통 다음 파일과 화면을 보게 된다.

| 위치 | 역할 |
| --- | --- |
| `exports/daily_news/` | 뉴스 리뷰 큐, 최종 브리프, GP 업데이트 작업 목록 |
| `exports/lp_commitment_monitor_latest.csv` | LP 공고 모니터 최신 결과 |
| `exports/gp_profile_master.csv` | GP 프로필 마스터 |
| `exports/people_profile_summary.csv` | 인물 프로필 요약 |
| `dashboard/data/dashboard_data.json` | 내부 콘솔용 데이터 |
| `services/newsletter/deploy/site/` | GitHub Pages로 배포되는 공개 사이트 bundle |
| `services/newsletter/deploy/site/data/service_data.json` | 공개 사이트 bundle용 public read model |

## 현재 완성도

현재 상태를 제품 관점으로 나누면 다음과 같다.

| 영역 | 현재 완성도 | 설명 |
| --- | --- | --- |
| 공개 서비스 구조 | 높음 | 브리프, LP, GP의 큰 메뉴 구조가 잡혀 있음 |
| 뉴스레터 | 높음 | 매일 수집, 리뷰, 최종 HTML, 배포 흐름이 존재 |
| FSS 기반 GP/Fund 데이터 | 중상 | FSS 적재, GP/펀드 마스터, 약정액 기준 분석이 가능 |
| LP 공고 모니터 | 중상 | LP 기관, 공고, 선정 GP 연결의 MVP가 있음 |
| GP 프로필 | 중간 | 핵심 GP 프로필 기반은 있으나 출처 보강과 품질 관리가 계속 필요 |
| People DB | 중간 | 스키마와 일부 데이터가 있고 GP 상세와 연결되기 시작함 |
| Wiki | 보류 | 공개 메뉴와 루틴 빌드에서 제외. 별도 기획 후 재개 |
| 내부 운영 콘솔 | 중간 | 데이터 확인과 운영 지표 역할은 있으나 서비스 운영 UX는 계속 개선 대상 |
| Deal DB | 낮음 | 장기 구상은 있으나 본격 데이터 모델과 화면은 아직 미구축 |

## 미완성 영역과 리스크

이 서비스가 더 완성도 높은 데이터 상품이 되려면 다음 영역이 중요하다.

| 영역 | 남은 과제 |
| --- | --- |
| 출처 품질 | 모든 GP/LP/People 프로필 값에 출처, 확인 상태, 날짜를 안정적으로 붙여야 함 |
| 이름 정규화 | 같은 GP, 펀드, LP가 다른 이름으로 나오는 문제를 계속 관리해야 함 |
| 화면과 DB의 연결 | DB에 있는 좋은 데이터가 공개 화면에서 자연스럽게 보이도록 정보구조를 다듬어야 함 |
| 공개/내부 분리 | 운영자용 작업 상태나 내부 표현이 공개 화면에 새지 않도록 계속 검증해야 함 |
| 반복 운영 | 수집, 리뷰, 빌드, 배포, 검증을 사람이 실수 없이 반복할 수 있는 런북이 더 필요함 |
| Deal DB | 뉴스에서 거래 후보를 뽑고, GP/펀드/타깃회사/자문사와 연결하는 별도 설계가 필요함 |
| Wiki 콘텐츠 | 단순 링크 모음이 아니라 실제 실무 문서형 콘텐츠로 계속 확장해야 함 |

## 이 서비스의 핵심 판단 기준

앞으로 기능을 추가할 때는 다음 질문으로 판단하면 된다.

| 질문 | 좋은 방향 |
| --- | --- |
| 이 데이터가 어떤 사용자 질문에 답하나? | 메뉴나 화면보다 먼저 사용자 질문을 정의한다 |
| 이 값의 출처가 있나? | 출처 없는 값은 추정하지 않고 비워 두거나 검토 상태로 둔다 |
| DB에 저장된 구조인가, 일회성 파일인가? | 반복 운영할 값은 DB나 관리 CSV에 남긴다 |
| 공개 화면에 보여도 되는 표현인가? | 내부 작업 상태와 운영자용 언어는 숨긴다 |
| 새 데이터가 화면까지 가는 경로가 있나? | 수집, DB, exports, public build, deploy까지 이어져야 한다 |
| 같은 이름 문제가 생기지 않나? | 표준 ID와 별칭 규칙을 먼저 확인한다 |

## 입문 용어집

| 용어 | 쉬운 설명 |
| --- | --- |
| 서비스맵 | 사용자가 보는 메뉴와 화면의 지도 |
| IA | Information Architecture. 정보구조. 화면과 콘텐츠를 어떤 순서로 배치할지 정한 구조 |
| 파이프라인 | 원천자료가 수집, 정제, 저장, 출력되는 자동 처리 흐름 |
| 워크플로우 | 사람이 포함된 실제 운영 순서 |
| 아키텍처 | 코드, DB, 파일, 배포가 어떻게 연결되는지에 대한 전체 구조 |
| DB | 서비스가 기억하는 정리된 데이터 저장소 |
| 스키마 | DB 안에 어떤 표와 컬럼이 있는지 정한 설계도 |
| 엔티티 | GP, Fund, LP, News, Person처럼 서비스가 관리하는 주요 대상 |
| 정규화 | 같은 대상을 같은 이름과 ID로 맞추는 작업 |
| ID | 이름이 바뀌어도 같은 대상을 가리키기 위한 고유번호 |
| Source Evidence | 어떤 사실의 출처와 근거 |
| Export | DB에서 뽑아낸 CSV, 엑셀, JSON 같은 산출물 |
| Static Site | 서버가 실시간 계산하지 않고 미리 만들어 둔 HTML/JSON을 보여주는 웹사이트 |
| Build | DB와 source 파일을 읽어 화면용 파일을 다시 만드는 작업 |
| Deploy | 만들어진 공개 파일을 실제 사용자가 보는 위치에 올리는 작업 |

## 한 줄 결론

이 서비스는 "뉴스 사이트"도 아니고 "단순 DB"도 아니다. 한국 PEF 시장의 원천자료를
GP, Fund, LP, News, People, 향후 Wiki라는 엔티티로 연결한 뒤, 내부 운영 콘솔과 공개 정적 웹서비스로
내보내는 데이터 상품이다.
